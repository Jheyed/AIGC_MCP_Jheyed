# 工作推进协议

版本：0.1  
状态：已采纳，可随实践调整（调整方式见 §8）

本协议只约束「沉淀与复用」，不约束执行细节。MCP 是稳定执行基座；上层能力通过一次次真实任务积累。

## 1. 一次任务等于一个循环

用户交流 → 真实执行 → 沉淀 → 回归 → 记录。

任务结束时必须产出「下次能直接调用的东西」。如果只产出了对话和一个能看的图，这个任务还没有收尾。

## 2. 产物只认三种

| 形态 | 位置 | 作用 |
|---|---|---|
| 配方 | `workflows/recipes/*.json` | 可提交的工作流与槽位 |
| 编译规则 | 代码中的纯函数 + 用例 | 自然语言 → 配方槽位 |
| 运行参数 | 配方槽位或运行器参数 | 步数、CFG、seed、尺寸 |

写着「以后要注意 X」的散文不算沉淀完成。

## 3. 单一真值源

每个事实只有一个家：配方参数住在配方 JSON 里，能力与限制住在知识条目里。其余文档只引用编号，不复述具体数值。

## 4. 知识条目的强制字段

| 字段 | 含义 |
|---|---|
| `id` | `K-NNNN`，全局唯一 |
| `statement` | 一句话结论，必须能被证伪 |
| `scope` | 适用的模型 / ComfyUI 版本 / 硬件 |
| `evidence` | `run_id` 或命令加输出路径 |
| `status` | `active` / `deprecated` / `superseded` / `needs-review` |
| `updated` | 日期 |

- 没有 `evidence` 的结论不得入库。
- 超出 `scope` 时，该结论视为「未知」，不得作为默认依据。
- 依赖的环境版本变化后，条目自动降级为 `needs-review`。

## 5. 任务类型是封闭清单

初始类型：文生图、改风格、角色定妆、改姿势、换镜头、批量、诊断、回归。

- 新增类型必须先证明「现有类型加一个参数做不到」。
- 两个类型的产物差异仅为参数时，强制合并为一个类型加参数。
- 上限 8 个；要超出时先做合并。

## 6. 变体只声明差异

变体配方只写相对基础配方的差异字段，不整份复制。差异超出白名单时按新配方对待，并写明理由。

## 7. 生命周期与收敛

每次同类任务收尾做一次收敛：重复项合并，失效项标为 `deprecated` 或 `superseded`。删除配方前必须确认没有回归用例引用它。

## 8. 冲突处理：原则与实际情况撞车时

出现下列任一情况，**先停下，不继续执行**，再决定改谁：

- 用户当次要求与本协议冲突；
- 按协议执行的成本明显高于收益；
- 实测证据推翻了协议里的既有假设；
- 同一条规则在近期被绕过两次以上。

处理顺序：先记录冲突事实，再判断属于「本次例外」还是「原则过时」。长期改变写 ADR；一次性例外记入本次任务记录，不追溯改写历史。

## 9. 记录上限

一次任务最多新增 1 个产物文件加 1 条 `CHANGELOG` 记录；其余信息靠引用。协议本身不超过一页，只定规则，不存数据。
