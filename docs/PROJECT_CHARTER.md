# 项目根本要求

版本：0.1  
状态：已采纳，可随项目演进但必须通过 ADR 记录重大改变。

## 1. 项目使命

建立一个面向缺少 ComfyUI 进阶经验用户的智能创作系统。用户通过自然语言描述创作目标，系统将其转换为可靠的 ComfyUI 执行方案，包括工作流选择、资产引用、参数配置、运行、结果获取和后续修订。

系统的价值不是简单地“远程控制节点”，而是把已经验证的 ComfyUI 专业知识转化为普通用户能够使用的目标级能力。

## 2. 最终目标

系统最终应支持：

- 自然语言控制本地 ComfyUI；
- 自动了解本机硬件、模型、节点和可用工作流；
- 角色参考一致性；
- 姿势、镜头、构图与风格控制；
- 可复用、可版本化的角色资产包；
- 可解释的工作流与参数选择；
- 完整的生成记录和结果复现；
- 有边界的视觉评价与自动修订；
- 多种 AI Agent 和人工命令行工具共同使用。

## 3. 不可破坏的根本约束

### 3.1 多 Agent 通用

- 核心接口采用公开标准，首选 MCP、JSON Schema、YAML/JSON 和普通文件路径。
- Codex 可以是首个开发与使用客户端，但不是运行所必需的唯一客户端。
- Agent 专属说明只作为适配层存在，不得成为唯一业务实现。
- 更换 Agent 后，角色包、工作流、运行历史和项目规则仍然有效。

### 3.2 优先复用成熟方案

- 每个重要组件在自建前必须完成现有方案调研。
- 优先级：官方方案 > 活跃且广泛使用的社区方案 > 小范围自建扩展 > 完全自建。
- 采用外部方案前记录版本、维护状态、许可、安全性和退出方案。
- 不为了“统一”而重写已经稳定工作的底层能力。

### 3.3 本地优先、云端可选

- 默认使用本地 ComfyUI、本地模型和本地资产。
- 云端模型、伙伴 API 或付费能力必须明确标识并由用户授权。
- 系统必须能够说明数据是否离开本机。

### 3.4 可解释与可复现

- 每次生成必须记录实际工作流、模型、seed、关键参数、输入资产和输出。
- 系统应能用普通语言解释为何选择某个方案。
- 不允许只保留最终图片而丢失复现信息。

### 3.5 安全的渐进自动化

- 第一阶段使用已验证的固定工作流配方。
- 只有具备验证、回滚和失败诊断后，才开放自动修改或构建工作流。
- 安装节点、下载大型模型、暴露网络端口和产生费用必须经过确认。
- 自动评价和重试必须设置轮数、时间或费用上限。

## 4. 目标用户

主要用户了解 AI 绘画的创作概念，但不应被要求掌握复杂节点图、采样器细节、插件兼容性或显存调优。

因此，面向用户的主要概念应是：

- 角色；
- 场景；
- 姿势；
- 镜头；
- 风格；
- 保持什么；
- 修改什么；
- 输出要求。

专业参数必须保留供检查和高级模式使用，但不应成为普通模式的必填项。

## 5. MVP 定义

第一版必须完成一条真实、可重复的纵向链路：

> 自然语言要求 + 一个角色包 + 可选姿势图 → 选择一个已验证工作流 → 本地 ComfyUI 生成 → 返回图片和完整运行记录。

MVP 不要求任意工作流自动构建，不要求自动解决所有角色一致性问题，也不承诺一次生成就满足主观审美。

## 6. 明确不做的事情

- 不把项目做成只对 Codex 有效的提示词集合。
- 不把 ComfyUI 的所有底层节点直接暴露给普通用户作为主要交互方式。
- 不在没有兼容性验证时自动安装大量 custom nodes。
- 不把在线模型包装成本地生成而不说明数据和费用去向。
- 不为了演示效果伪造成功状态、生成记录或测试结果。

## 7. 成功标准

- 新用户可用自然语言完成常见生成任务。
- 至少两个不同 Agent 客户端可调用同一核心能力。
- 同一次运行可在环境允许时根据记录复现。
- 失败信息能指出缺少的模型、节点、资产或资源限制。
- 一个新的 Agent 仅阅读项目文档即可继续开发，不依赖上一位 Agent 的对话历史。
