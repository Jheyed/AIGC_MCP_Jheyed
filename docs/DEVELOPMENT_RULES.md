# 协作与编辑规范

## 1. 工作流程

### 修改前

1. 阅读项目根本要求和当前状态。
2. 检查已有文件、未提交修改和依赖状态。
3. 明确本次工作单元的目标、范围和验收方式。
4. 涉及外部框架时，先核实官方文档、版本、许可和维护状态。

### 修改中

1. 保持小步、可验证。
2. 优先修改现有抽象，不重复建立相同概念。
3. schema、示例、文档和实现应同步更新。
4. 发现原计划不成立时先记录证据，再调整方向。
5. 不覆盖与当前任务无关的用户或其他 Agent 修改。

### 修改后

1. 运行检查或测试并记录真实结果。
2. 更新 `CHANGELOG.md`。
3. 更新 `docs/STATUS.md`。
4. 重大决策新增 ADR。
5. 检查是否引入专属 Agent 依赖、秘密信息或绝对个人路径。

## 2. 变更日志规则

每个完成的工作单元都必须在 `CHANGELOG.md` 的 `Unreleased` 中留下记录。记录包括：

- 日期；
- 变更内容；
- 变更原因；
- 验证方式和结果；
- 相关 ADR（若有）。

不要把每次保存文件写成一条日志。多次编辑只要属于同一目标，应合并为一个可审阅的工作单元。

## 3. 架构决策记录

符合以下任一条件时新增 ADR：

- 选择或替换关键框架；
- 引入长期外部依赖；
- 修改公开 schema 或 MCP 工具契约；
- 改变安全、费用或隐私边界；
- 放弃一个此前采纳的重要方向。

ADR 一经接受不直接覆写结论。方向改变时新增 ADR，并将旧 ADR 标为被替代。

## 4. 状态与交接

`docs/STATUS.md` 只保存当前有效状态，不堆积完整历史。完整历史在 Git、变更日志和 ADR 中。

状态文件必须回答：

- 现在完成到哪里；
- 当前验证过什么；
- 有哪些问题和风险；
- 下一步最合理的工作是什么；
- 是否等待用户决定或授权。

## 5. 版本控制

- 提交应围绕一个目的组织。
- 提交信息说明意图，而不只是列文件名。
- 不提交模型权重、生成缓存、密钥、虚拟环境和大型临时输出。
- 外部项目代码不得直接复制进来而不保留来源和许可证信息。

## 6. 文档写法

- 面向用户的文档使用普通语言，首次出现专业词时解释。
- 技术规则应明确区分“必须”“应该”“可以”。
- 示例必须标注是示意还是已经验证。
- 不把未来设想写成已经实现的功能。

## 7. 安全与授权

下列操作必须获得用户确认：

- 下载大型模型或显著占用磁盘的依赖；
- 安装、更新或删除 custom nodes；
- 修改现有 ComfyUI 安装；
- 调用付费服务；
- 将本地服务暴露到局域网或公网；
- 删除用户资产、生成记录或模型。
